# Структурированные планы

Новый интерфейс доступен по `/` того же FastAPI-сервера. `matrix.html` сохраняет первоначальный автономный прототип матрицы. API рассчитан на одного пользователя; публичное размещение Python-сервера требует отдельной авторизации.

## Цепочка

1. Создать проект через `POST /api/projects` (см. `memory-api.md`).
2. Запросить предложение: `POST /api/projects/{id}/plans/propose` с `request_id`, `base_revision`, `text`.
3. Посмотреть `plan.proposal` и `plan.validation`. До принятия это черновик.
4. Принять: `POST /api/projects/{id}/plans/{plan_id}/accept` с новым `request_id` и актуальной `base_revision`.
5. Оспорить решение следующим запросом `plans/propose`. В модель передаются принятый план, последнее предложение, возражения из диалога, подтверждённые условия, статусы задач и последние события.

Для чтения всего экрана: `GET /api/projects/{id}/workspace`. Ответ содержит проект, принятую версию, новое предложение, различия, статусы задач, историю, текущую проверку выполнимости и оценку размера памяти диалога.

## Что проверяет код

- Уникальные идентификаторы задач, корректные зависимости и отсутствие блокирующих циклов.
- Сумму оценок оставшейся работы и резерва относительно доступного времени.
- Дедлайн и доступные рабочие интервалы. Задача может занимать несколько интервалов; следующая зависимая задача начинается после её завершения.
- Наличие критериев успеха и известных доступных минут.
- Ссылки на подтверждённые требования: нумерация `constraint_refs` начинается с 1. Это проверка покрытия ссылками, а не доказательство смыслового выполнения требований.
- Сохранение закреплённых и выполненных задач, их названий и критериев готовности.
- Явное исключение прежних задач через `decision=defer` и объяснение компромиссов для переноса/упрощения.
- Актуальность ревизии непосредственно перед записью и повторно перед принятием.

Модель получает конкретные ошибки валидатора и может исправить предложение; максимум три обращения на одну операцию. Фактические проверки хранятся в `validation.generation_checks`, статистика каждого обращения — в usage сообщения. Если не хватает сведений пользователя, вопросы возвращаются без бессмысленных повторов. Если исправления не привели к выполнимому плану, черновик остаётся неприменимым. Некорректный JSON после всех попыток не создаёт версию плана.

Числа времени являются оценками, а не измерениями. Код проверяет согласованность плана с этими оценками; реальные длительности и смысловые обоснования проверяет пользователь.

## Задачи и события

`PATCH /api/projects/{id}/tasks/{task_id}`:

```json
{
  "request_id": "d9349ca8-e4a7-4d51-ad14-bcc539840bf1",
  "base_revision": 2,
  "done": true,
  "actual_minutes": 45
}
```

`actual_minutes` необязательно: без него используется оценка принятой задачи. Завершение уменьшает оставшееся время. При возврате задачи в работу списанное значение восстанавливается. Завершение требует выполненных зависимостей; сначала возвращаются в работу завершённые зависимые задачи. Для закрепления передайте `pinned: true` (без `done`).

`POST /api/projects/{id}/events/time-lost` принимает `request_id`, `base_revision`, `minutes`. Остаток времени уменьшается до нуля включительно; событие фиксируется отдельно. В интерфейсе после события автоматически запрашивается новый план. Если запрос модели не удался, событие остаётся сохранённым, а старый план доступен для сравнения.

Изменение условий через `PATCH /api/projects/{id}` также записывается в историю. Можно передать новое `title`; состояние передаётся целиком.

Рабочие интервалы — необязательное поле `state.work_windows`:

```json
[
  {"start":"2030-11-01T18:00:00+03:00", "end":"2030-11-01T21:00:00+03:00"}
]
```

Интервалы должны содержать часовой пояс, положительную длительность и не пересекаться. Без них интерфейс показывает последовательность работ; календарное расписание не подразумевается.

## Память и размер полного запроса

Окно памяти показывает вход для контекста диалога и канонические факты проекта. Запрос планирования дополнительно содержит схему ответа, планы, статусы задач и события; бюджет проверяется для полного запроса, включая обратную связь при исправлениях. Фактические input/completion tokens каждого обращения сохраняются из ответа провайдера. Перед каждой попыткой выполняется точный подсчёт токенов полного запроса и при достижении порога автоматически сжимается журнал диалога с сохранением версий. Схема ответа, факты, планы, события и свежий запрос сохраняются целиком. Доступны также кнопка и `/compress`.

## Два режима интерфейса

- При запуске с FastAPI интерфейс обращается к настоящему YandexGPT, а данные хранятся в серверной БД.
- При статическом размещении без API или параметре `?demo=1` используется явно обозначенный демонстрационный сценарий. Он хранится в браузере, не обращается к модели, поддерживает потерю времени, спор об анимациях, принятие и завершение задач. Для произвольного ввода сообщает о границах демо. Сжатие и редактирование произвольных проектов доступны в реальном режиме.

API-ключ остаётся в локальном `.env`. В статическую публикацию входят только файлы `frontend/dist` и конфигурация Sites.

## Пересчёт без изменения работы

Если структура работы, оценки, приоритеты, зависимости, критерии готовности, ссылки на требования, порядок задач и резерв совпадают с принятым планом, новая формулировка объяснений не требует повторного принятия. Ответ и предложение сохраняются в журнале и истории; `validation.unchanged` отражает результат сравнения при генерации. `workspace.draft` в таком случае отсутствует. Изменение только текста summary/reason/assumptions/risks не заменяет принятый план.

Основная вкладка интерфейса показывает принятые задачи, новое предложение доступно для сравнения в «Изменениях». Пока пользователь обсуждает предложение, он может продолжать завершать принятые задачи. Такое действие обновляет revision; предложение при необходимости пересчитывается перед принятием.
