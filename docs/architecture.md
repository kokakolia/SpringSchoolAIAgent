# Архитектура

```mermaid
flowchart LR
    UI[Интерфейс] --> API[FastAPI]
    API --> State[Состояние и журнал]
    API --> Guard[Подсчёт токенов и сжатие]
    Guard --> LLM[YandexGPT]
    LLM --> Schema[Проверка JSON]
    Schema --> Rules[Время, зависимости, закрепления]
    Rules --> Draft[Предложение и сравнение]
    Draft --> Accept[Принятие пользователем]
    State --> DB[(PostgreSQL / SQLite)]
    Accept --> DB
```

## Почему агенту можно возражать

Канонические факты проекта хранятся отдельно от текста диалога. Сгенерированный план
сначала становится предложением. Сервер считает время, проверяет зависимости и защищённые
задачи. Пользователь видит различия и причины, затем явно принимает вариант.
Невалидное предложение не может стать принятым планом.

## Память и контекст

Полный журнал сообщений не удаляется. Рабочий контекст состоит из системной инструкции,
актуальных фактов, последней сводки и сообщений после её границы. Для планирования
добавляются схема ответа, текущий и последний предложенный планы, прогресс и события.
Перед каждым запросом и повторной попыткой проверяется точный размер полного ввода.

Автоматическое сжатие готовит две версии в памяти процесса. Они записываются вместе
с ответом одной транзакцией и одним увеличением revision. Ошибка модели или конкурирующая
правка оставляет прежний контекст и журнал неизменными. Канонические факты и свежий
запрос не сжимаются. Команда `/compress` остаётся доступной отдельно.

## Надёжность

- UUID запроса делает успешный повтор идемпотентным.
- Запись блокировки в БД не допускает параллельные обращения к модели в одном проекте, включая разные процессы сервера.
- Сравнение revision при записи предотвращает потерю параллельных правок.
- Сетевые вызовы выполняются вне транзакций базы данных.
- Миграции запускаются транзакционно; PostgreSQL использует advisory lock при старте.
- PostgreSQL и SQLite проверяются одним набором тестов; внешняя сеть в тестах отключена.
- UI показывает отправленное сообщение сразу и согласует его с серверным журналом по UUID.

## Границы

Ссылки задач на обязательные требования проверяются по номерам, без независимой
семантической оценки. Сервер не доказывает реалистичность оценок времени, созданных моделью.
Доступ защищён режимом localhost и сессиями для одного владельца при настроенном пароле. Раздельные аккаунты пользователей, командная работа и самостоятельное выполнение задач пока не реализованы.
Статическое демо использует сценарий в браузере; настоящий агент работает с API и БД.

## Защита входа и браузера

Без `APP_PASSWORD` доступны только запросы от loopback-клиента с локальным Host. Проверки Origin и Sec-Fetch-Site отклоняют чужие сайты, в том числе на чтение API. При заданном пароле вход через форму или HTTP Basic создаёт сессию: пользователь `APP_USERNAME` (по умолчанию owner), пароль от 16 символов. Для внешнего клиента по умолчанию требуется HTTPS. Исключение `/health` сообщает только состояние процесса. Ответы запрещают iframe-встраивание; данные API не кешируются браузером.

Для публичного размещения используйте HTTPS-прокси с корректно настроенным доверием к forwarded-заголовкам. `APP_ALLOW_HTTP=true` допустим только в доверенном локальном режиме; Compose использует его из-за сетевого шлюза Docker и публикует порт исключительно на 127.0.0.1. Пустой пароль не разрешает доступ со шлюза Docker.


Неудачные входы ограничены: 10 на адрес клиента и 100 суммарно за минуту на процесс
сервера. Ответ `429` содержит Retry-After; по окончании окна вход снова доступен.
Счётчики ограничены по памяти. Для нескольких процессов или экземпляров общий лимит
на уровне развёртывания задаётся на HTTPS-прокси; встроенные счётчики не разделяются между ними
и очищаются при перезапуске. Доверяйте forwarded-заголовкам только от своего прокси.

Старый `/api/process` отвечает 410 без вызовов модели; прежний AI-цикл удалён.
Старые HTTP-операции матрицы удалены; историческая таблица доступна только через выгрузку JSON в CLI.


Тела изменяющих HTTP-запросов ограничены 1 МиБ (`MAX_REQUEST_BYTES`). Проверяется
фактически прочитанный объём, включая потоковые запросы без Content-Length.
Контейнер запускается без прав root. Обычный запуск сервера не включает reload;
режим наблюдения за исходниками включается только флагом --reload.


Проверка нового пароля допускается только до исчерпания лимита попыток. Уже
аутентифицированный владелец продолжает работу по отдельной сессии. Новый вход после
исчерпания лимита ждёт конца окна, даже если пароль правильный. Это предотвращает
проверку дополнительных догадок через различие 429/200. Лимиты в процессе дополняются
ограничениями на HTTPS-прокси при нескольких процессах или экземплярах.

Сессии — случайные 256-битные токены в HttpOnly/SameSite=Strict cookie; HTTPS использует
Secure и префикс __Host-. В БД находятся только хеш токена, срок и HMAC-привязка к текущим
центральным учётным данным. Пароль не сохраняется в сессии. Административная ротация,
истечение срока или POST /auth/logout прекращают действие сессии. Локальный режим
без пароля остаётся доступным только с loopback и локальным Host.


Тело формы входа ограничено 4096 байтами и общим сроком
AUTH_LOGIN_BODY_TIMEOUT_SECONDS (5 секунд). Срок не продлевается каждым новым фрагментом;
при превышении сервер отвечает 408. Одновременно проверяются не более
AUTH_MAX_CONCURRENT_LOGINS (8) запросов на процесс; лишние получают 503 с Retry-After.
Резерв попытки снимается при успехе, ошибке, тайм-ауте, отключении и отмене.
Глобальный и адресный лимиты учитывают завершённые неудачи плюс текущие проверки;
успех не уменьшает чужие ошибки и не расходует лимит неудачных входов.

Версия учётных данных хранится в auth_credentials. Проверка сессии только читает эту
запись, хеш токена и срок: запрос без cookie не обращается к таблице сессий и ничего
не меняет. HMAC новых токенов привязан к центральному verifier, а не локальному паролю
процесса. Владелец с действующей новой сессией может обращаться к обновлённым процессам
с конфигурацией A и B; процесс с устаревшей конфигурацией отклоняет новые входы с 503,
не расходуя лимит паролей. Пустой локальный пароль также не позволяет обойти центральную
защиту: при несовпадении настроек анонимный локальный доступ закрыт.

Запуск только создаёт начальную запись при её отсутствии. Существующая версия не
переписывается. Изменение APP_PASSWORD/APP_USERNAME применяется отдельной локальной
командой auth-update с ожидаемой версией из auth-status. Операция сравнивает generation,
атомарно увеличивает её, заменяет солёный PBKDF2-HMAC-SHA256 verifier (200000 итераций)
и удаляет прежние сессии. Два обновления одной версии не могут одновременно пройти;
запросы и запуск старого процесса не могут откатить центральные настройки.
Возврат прежнего пароля тоже является явной ротацией с новым поколением.

При первом переходе на эту реализацию замените все процессы с прежним кодом,
автоматически изменявшим generation. Такой старый код с правами записи в ту же БД
по-прежнему способен менять таблицы. Куки прежнего формата могут потребовать нового
входа. После обновления кода процессы с разными конфигурациями безопасно читают одну
центральную версию; новую ротацию выполняет только администратор.
